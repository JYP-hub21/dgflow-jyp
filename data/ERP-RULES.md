# 발주서 → ERP 업로드 엑셀 변환 규칙

실제 업무 흐름은 **발주서 → 규격정리 → ERP 업로드 엑셀 → (회사 ERP) → 작업의뢰서**다.
DG-Flow가 대체하는 구간은 발주서에서 ERP 업로드 엑셀까지고, 최종 산출물은 작업의뢰서가 아니라
**ERP에 넣을 엑셀**이다. 작업의뢰서는 ERP가 뽑아 준다.

## 검증 근거

| 자료 | 내용 |
|---|---|
| `발주서(우미건설-남원주 역세권1차) (11).xlsx` | 18시트. 1차~8차 + 파손분 + 물량산출서 |
| `규격정리-우미건설.xlsx` | 현장별 7시트. 남원주 역세권 = 4,119행 (7차는 `DCE6F2` 파란색, 2744~3137행) |
| `ERP-2026년.xlsx` | 사람이 손으로 만든 실물. `우미 남원주7차` 계열 9시트 |

발주서 7차에서 규칙대로 생성한 결과를 실물 ERP 9시트와 대조했다 (`__tests__/erp-upload.test.ts`):

- **136행 전체 규격(가로·세로)·수량 일치**
- **위치 문자열 118행 글자까지 일치** (실물 수기 오타 7건 보정 후)
- 나머지 18행은 실명이 갈리는 행 — 아래 "판단이 필요한 부분" 참고
- 시트 배치 순서도 실물과 일치

## 규격정리는 재현하지 않는다

규격정리 엑셀은 발주서에 없는 정보를 만들지 않는다. 하는 일은 셋뿐이다.

1. 품명을 사내 표기로 바꾼다 (`5GN+12Ar+5DURA MAX` → `22T 5newGN+12AR.+5로이`)
2. 평·M2를 계산한다
3. ERP 순서로 재배열한다 — 좌측 블록은 발주서 순서(가로 오름차순), 우측 블록은 ERP 순서

그래서 발주서에서 ERP 엑셀을 직접 만든다. 규격정리의 날짜 칸은 발주서에서 유도되지 않는 별도 입력값인데
사용자 확인 결과 **비워 둬도 되는 값**이다.

## 발주서에서 읽는 것

차수 시트(`1차`~`8차`) 기준. 상단은 자유 서식이라 라벨을 찾아 옆 칸을 읽는다.

| 위치 | 내용 |
|---|---|
| H2 | 발주번호 — **1차~4차는 다른 현장(`대원-용인에버랜드`) 값이 남아 있다.** 현장 식별에 쓰면 안 된다 |
| B4 / H4 | 공사명 / 시공자 |
| B6 / B7 | 발주일 / 출고일 |
| A11 | 포장 지시 + **동순서** (`※ 7차(31~25F) … (동순서 3-4-2-1-5)`) |
| A12 | 포장 단위 (`1,3,4동( 1,2,3호 포장,4,5호 포장),2동(…), 5동(…)`) |

품목은 13~14행 2단 헤더, 15행부터. `A`=위치(2줄: `1동 1호` / `84A 31~35F`) · `B`=제품명 ·
`C`=두께 · `D`=가로 · `E`=세로 · `F`=수량 · `I`=동호 · `J`=실명+창구분.

호 하나마다 제품명 블록 3개가 붙고 각각 `계` 행으로 끝난다.

| 블록 | 발주서 제품명 | 대상 | 사내 품명 |
|---|---|---|---|
| 1 | `5GN+12Ar+5DURA MAX` | 실별 `(外)` — 외창 | `22T 5newGN+12AR.+5로이` |
| 2 | `5CL+12Ar+5DURA MAX` | 실별 `(內)` — 내창 | `22T 5CL+12Ar.+5로이` |
| 3 | `5GN+12Air+5DURA MAX` | 발코니1, 하향식피난구 | `22T 5newGN+12A+5로이` |

`Ar`(아르곤)은 `AR.`, `Air`(공기)는 `A`, `DURA MAX`는 `로이`로 적는다.

**포장 경계는 제품명 열(B)의 `"N동 x,y호 같이 포장"` 행이다.** 3차부터 들어 있고, 각 포장 그룹의
마지막 다음 줄에 놓여 닫는 구분자로 동작한다. 7차의 9개가 ERP 시트 9장과 1:1로 맞는다.
(두께 열은 1차~8차 전부 `22` 하나뿐이다.)

### 포장 단위를 찾는 순서 (`lib/erp/packaging-note.ts`)

1. 품목 영역의 **"같이 포장" 표시행** — 동·호가 명시돼 가장 정확하다 (3차부터)
2. 상단 **포장 지시문** — `1,3,4동( 1,2,3호 포장,4,5호 포장),2동(…)`
3. 품목의 **동·호 조합에서 동별 추론** — 1차·2차처럼 포장 단위 문장이 없을 때
4. 동·호도 못 읽으면 전체 한 장

⚠️ **11행을 포장 단위로 쓰면 안 된다.** 11행은 `※ 7차 주문서별 포장요망 (동순서 3-4-2-1-5)` 이고
정작 포장 단위는 12행에 있다. "포장" 이 들어간 첫 줄을 집으면 11행에 걸려 전체가 한 장으로 떨어진다.
(실제로 그 버그가 있었다 — `__tests__/erp-packaging-detect.test.ts` 가 회귀를 막는다.)

1차·2차는 `※ 동별,라인별 포장요망` 뿐이라 포장 단위 문장이 아예 없다. 이때는 동별로 나누고
"추론" 이라고 알린다. 화면에서 **동별 / 동·호별 / 나누지 않기** 로 바꿀 수 있다.

## ERP 업로드 양식

**4열: `위치 | 규 | 격 | 수량`.** 1행이 헤더이고 `규`·`격`이 가로·세로 칸에 나눠 적힌다.
**품명 열이 없다** — 품명은 ERP 화면에서 지정한다.

**시트 1장 = 포장 1개 = 작업의뢰서 1장.**

시트 안 행 순서:

1. `(外)` 블록 전체 — 세로 내림차순 → 가로 내림차순
2. `(內)` 블록 전체 — 같은 정렬
3. 발코니1 / 하향식피난구

**호 병합**: 같은 품명 블록에서 `(가로, 세로)`가 같으면 여러 호를 한 줄로 합치고 수량을 더한다.

위치 문자열 = `{동}동 {호} {타입} {층}F {실명}({內/外})`

| 항목 | 규칙 | 예 |
|---|---|---|
| 호 | 3개 이상 연속이면 `~`, 그 외는 콤마 | `1~3호` · `4,5호` · `1,3호` |
| 타입 | 공통 숫자 접두 + 접미사 **알파벳순** | `84A,B` · `84A,C` (2동은 호 순서가 C→A인데도 `84A,C`) |
| 층 | 그대로 | `31~35F` |

**시트 배치 순서 = A11의 동순서.** 7차는 `3-4-2-1-5`이고 실물 ERP의 시트 배치가 정확히 그 순서다
(3동 1~3호, 3동 4,5호, 4동 1~3호, 4동 4,5호, 2동 1,2호, 2동 3~5호, 1동 1~3호, 1동 4,5호, 5동 1~3호).
현장에서 그 순서로 싣기 때문이다. 시트명의 `(2)`, `(3)`… 은 엑셀 복사 시 자동 번호라 순서와 무관하다.

## 판단이 필요한 부분 — 채우지 않는다

발주서는 양식이 같아도 작성자마다 내용이 다르다. 아래는 **자동 판정이 불가능함이 증명된** 항목이다.

### 실명 선택 (규칙 없음)

여러 호를 한 줄로 합칠 때 호마다 실명이 다르면 어느 것을 쓸지 규칙이 없다.

> 5차와 7차의 발주서 3동 1~3호 455×950 데이터가 **완전히 같은데**,
> 5차 작업의뢰서 스캔본에는 `주방/식당`, 7차 ERP 엑셀에는 `주방/식당,드레스룸`으로 적혀 있다.

같은 입력을 사람이 다르게 쓴 것이다. 시스템은 **첫 값을 넣고 확인 요청을 띄우는 것까지**만 한다.

### 그 밖에 비워 두는 것

- 위치 조각(동·호·타입·층·실명)을 못 읽으면 **그 조각만 빠진 채로** 둔다. 추측해서 채우지 않는다.
- 포장 지시문을 못 읽으면 동별로 나누고 "추론" 이라고 알린다. 동·호까지 못 읽으면 전체 한 장으로 둔다.
- 어느 포장에도 안 들어간 품목은 버리지 않고 엑셀의 `_미배정` 시트로 함께 내려보낸다.

## 실물 ERP 파일의 수기 오타

자동 생성하면 사라지는 차이다. 테스트에서 `KNOWN_TYPOS`로 보정한다.

| 실물 | 올바른 값 |
|---|---|
| `3동 1~3호 84A,B 31~36F 주방/식당,드레스룸(外/內)` | `31~35F` |
| `4동 2,3호 84A,B 31~38F발코니1` | `31~35F 발코니1` |
| `4동 1~3호 … 주방/식당,드레스(外/內)` | `주방/식당,드레스룸` |
| `2동 3~5호 84A,B31~35F 거실F(外)` | `84A,B 31~35F` |
| `2동 4,5호 84A,B 31~35F발코니1` | `31~35F 발코니1` |

## 아직 모르는 것

- **ERP 시트명 규칙** — `우미 남원주7차`는 `{거래처}{현장}{차수}`인데 `우미장안1,2동 최상`처럼 동·층이 들어가는 것도 있다. 사람이 알아보기 편하게 붙이는 이름으로 보여 지금은 포장 라벨(`3동 1~3호`)을 쓴다.
- **5동 4,5호** — 포장 지시에 5동은 `1,2,3호`만 있다. 세대가 없는 건지 다른 차수로 빠진 건지 미확인.

# KCC건설 여의도 오피스텔 — 두 번째 양식

우미와 **같은 양식인데 위치를 적는 칸이 다르다.** 두 실물을 같이 놓고 보니
동일유리 표준 발주서 양식이 거래처마다 다르게 쓰이고 있음이 드러났다.

## 검증 근거

| 자료 | 내용 |
|---|---|
| `엑셀 자료/KCC건설 여의도오피스텔 발주서.xlsx` | 23시트 (발주일자별). 검증은 `2026.09.17` |

`__tests__/erp-kcc.test.ts` 에서 **ERP 실물 64행 전부 위치·규격·수량이 글자 단위로 일치**한다.
우미와 달리 위치 오타 보정이 하나도 필요 없었다 — 조립하지 않고 발주서 원문을 그대로 쓰기 때문이다.

## 우미와 무엇이 다른가

| | 우미 남원주 | KCC 여의도 |
|---|---|---|
| 헤더 행 | 13 | 12 |
| `위 치` 열 | `1동 1호` / `84A 31~35F` 로 채움 | **23개 시트 전부 비어 있음** |
| `비 고` 열 | `1동 1호` (중복) | **`근생/1층/38/AW 우스텝-1W:920` ← 진짜 위치** |
| 위치 만드는 법 | 동·호·타입·층·실명을 조립 | **비고 원문 그대로** |
| 포장 단위 | 상단 지시문 | **회색 합계 행** |
| 같은 규격 병합 | 여러 호를 한 줄로 합침 | **합치지 않음 (1:1)** |
| 총계 행 | 없음 | 있음 |

**열 이름을 믿으면 안 된다.** `위 치` 라는 이름의 열이 통째로 비어 있고 진짜 위치는 `비 고` 에 있다.
그래서 이름이 아니라 **실제로 채워진 내용**으로 고른다 (`pickLocationSource`).

## 블록 구조와 세 가지 합계 행

품명 칸은 블록마다 **2단**이다. 첫 줄이 품명, 둘째 줄이 사양이다.

```
[C15] 5MVT172 H/S+ 14Ar + 5CL(근생)   ← 품명
[C17] 단열간봉/알곤/구조마감            ← 사양 (품명이 아니다!)
 ... 본문 ...
[E25] 계  [F25] 12                     ← 블록 끝
```

둘째 줄을 품명으로 읽으면 **모든 블록이 `단열간봉/알곤/구조마감` 하나로 뭉쳐** 정렬이 무너진다.
23개 시트 전부에서 사양 줄은 `단열간봉/알곤` 또는 `단열간봉/알곤/구조마감` 두 가지뿐이었다.

합계 행 세 가지는 **모양으로** 갈린다.

| 행 | 모양 | 뜻 |
|---|---|---|
| 25행 | 가로 칸에 `계` | 품명 블록 끝 |
| 48행 | 가로·세로 비고 수량만 있음 | **포장 끝** (회색 합계) |
| 97행 | 품명 칸에 `총 계` | 시트 총계 |

## 포장 = 회색 합계 행

11행에 `※ 회색 합계 단위로 포장부탁드립니다.` 가 **23개 시트 전부** 적혀 있다.

9/17 시트: 48행 `56` = 블록1(12) + 블록2(44), 95행 `47` = 블록3(41) + 블록4(6), 총계 103.
실물 ERP 두 시트가 정확히 56장 / 47장이다.

합계 행에 라벨이 있으면 그게 포장 이름이다 — `A-구간 합계` · `5층 합계` · `HOIST-A 합계`.

## 위치 문자열

**ERP 위치 = `구조마감 ` 접두(선택) + 발주서 비고 원문 + 비고에 빠진 보조 열 값**

- 접두: 블록의 사양 줄에 `구조마감` 이 있으면 붙는다. `10CL T/P` 블록은 사양 줄이 없어 접두도 없다.
- 보조 열: 비고 오른쪽 `계약 | 층 | 도면부호 | 스텝라벨 | 내판폭` 은 비고를 쪼개 놓은 값이다.
  대부분 비고에 이미 들어 있지만 **내판 폭(`W:1385`)만 빠져 있고, 실물 ERP에는 붙어 있다.**
  그래서 "비고에 없는 보조 열 값" 을 구분자 없이 이어 붙인다 (`우스텝-2` + `W;920`).
- 더 오른쪽에 **전혀 다른 표**(품명·도면부호·가로·세로·수량)가 하나 더 있다. 그걸 붙이면 안 되므로
  "그 열 값이 비고에 들어 있던 적이 한 번이라도 있는가" 로 보조 열 구간을 끊는다.

스텝 유리의 내판은 별도 행이 아니다 — 위치 문자열의 `W:920` 이 전부다.
발주서 82·84·86행처럼 가로만 있고 세로·수량이 빈 행은 내판 표시이므로 품목으로 세지 않는다.

## 병합하지 않는다

실물 ERP에 `구조마감 근생/1층/41/AW · 1345×2830 · 4` 가 **두 줄** 들어 있다 (발주서 60·78행).
합쳐서 8장 한 줄로 만들면 안 된다.

우미(합침)와 KCC(안 합침)를 모두 설명하는 규칙:

> **위치가 서로 다를 때만 합친다.** 위치가 완전히 같은 두 줄은 발주서가 같은 내용을 두 번 적은 것이므로
> 사람이 보고 판단해야 한다 — 말없이 합치면 중복 발주인지 정상인지 구분할 방법이 사라진다.

우미에서 합쳐진 행들은 호가 서로 달랐다(`3동 1호`+`2호`+`3호` → `3동 1~3호`).
본질은 "수량 더하기" 가 아니라 "여러 호를 하나로 묶기" 였다.

## 연번이 붙은 블록은 정렬하지 않는다

스텝 블록(`우스텝-1`…`좌스텝-2`)은 실물 규격정리에서 **좌(발주서 순서)와 우(ERP 순서)가 완전히 같다.**
사람도 재배열하지 않았다. 다른 블록은 전부 세로↓ 가로↓ 로 재배열돼 있다.

번호 자체가 발주자의 순서 지시로 보이므로, 블록의 모든 위치에 `이름-숫자` 연번이 있으면
발주서 순서를 그대로 둔다. 화면에는 그 사실을 한 줄로 알린다.

## 발주서 자체의 오류

검산을 붙이자 **발주서의 합계 수식이 깨진 시트 두 개**가 바로 드러났다.

| 시트 | 총계 칸 | 블록 계 합 |
|---|---|---|
| `2026.06.08(호이스트제외전층물량)` | `118.33333` | 120 |
| `2026.06.29(발주누락) (2)` | `5.33333` | 8 |

장수는 정수여야 하므로, 정수가 아닌 합계는 검산 기준으로 채택하지 않고 사람에게 알린다.
고쳐 주지 않는다 — 발주서가 틀렸는지 우리가 틀렸는지는 사람이 판단할 일이다.

## 검산 — 발주서에게 되묻기

"모든 발주서 양식을 완벽히 이해한다" 는 불가능하다. 하지만 **"이 발주서를 제대로 읽었는지" 는
발주서 자신에게 물어볼 수 있다.** 블록 `계`, 포장 `합계`, `총계` 가 이미 정답이다.

`lib/erp/reconcile.ts` 가 우리 계산과 이 숫자들을 대조해 화면 맨 위에 띄운다.
전부 맞으면 사원은 믿고 넘어가고, 어긋나면 어느 블록인지 바로 짚인다.

## 규격정리도 만들어 준다

좌측 블록 = 발주서 순서 그대로, 우측 블록 = ERP 순서임을 실물에서 확인했으므로
규격정리 엑셀 자체를 생성할 수 있다 (`lib/erp/spec-sheet.ts`).

`평` 이라고 적힌 열은 실제로는 **재(才)** 다. 828행 `195×540×1` 의 값 `1.1469463778060975` 를
면적 0.1053 m² 로 나누면 0.091809 = 0.303² 이 나온다 (1재 = 303mm × 303mm).
1평 = 3.3058 m² 로 계산하면 실물과 전혀 맞지 않는다.

**사람이 채울 칸은 품명 하나뿐이다.** 발주서 품명을 ERP 품목명으로 바꾸는 일은 규칙이 없다
(`10CL T/P` → `24T 5MVT172+14단열(Ar.)+5CL`). 그래서 발주서 품명을 그대로 적어 내보낸다.

## 양식 프로파일

자동 판정이 실패하는 양식은 앞으로도 계속 들어온다. 그래서 만능 파서를 만드는 대신
**한 번 가르치면 기억하게** 했다 — 사원이 화면에서 열을 찍으면
`dgflow_order_form_profiles` 에 저장되고, 같은 거래처의 다음 발주서에 자동 적용된다.
매칭 근거는 헤더 지문(가장 강함) → 현장명 → 거래처명 순이고, 근거가 하나도 없으면 적용하지 않는다.

# 포장 직접 짜기 — 발주서가 애매할 때

발주서에 포장 단위가 명확히 적혀 있으면 자동으로 나눈다(회색 합계 행 / 포장 지시문 / 동·호).
하지만 작성자마다 적는 방식이 달라 알아보기 힘든 발주서가 계속 들어온다.
그때 사원이 직접 행을 골라 포장을 짠다 (`components/erp/PackagingEditor.tsx`).

## 지키는 것

| | 왜 |
|---|---|
| **빈 화면에서 시작하지 않는다** | 자동 결과를 복사해 놓고 틀린 것만 옮기게 한다. 103행을 처음부터 배정하게 만들면 아무도 쓰지 않는다 |
| **행을 잃어버릴 수 없다** | 미배정 행을 붉게 띄우고, 남아 있으면 다운로드 버튼에 경고를 건다. `_미배정` 시트로도 내려간다 |
| **발주서 행 번호를 보여 준다** | 사원이 발주서 원본과 나란히 놓고 대조해야 한다 |
| **한 행은 한 포장에만** | 다른 포장으로 옮기면 원래 포장에서 자동으로 빠진다 |

빠른 선택은 품명 블록 / 동 / 동·호 / 층 / 위치 기준으로 칩을 만들어 준다.
값이 2종 이상 나오는 기준만 화면에 띄우므로, 동·호가 없는 근생 발주서에서는 품명 블록만 나온다.

## 저장 — 행 번호가 아니라 기준을 저장한다

짠 구성을 **발주서 행 번호로 저장하면 다음 차수에 못 쓴다.** 행이 밀리기 때문이다.
그래서 저장할 때 무엇을 기준으로 묶었는지를 뽑아낸다 (`lib/erp/packaging-rule.ts`).

| 뽑아낸 기준 | 조건 | 재사용 |
|---|---|---|
| `units` | 한 동의 특정 호들이고, **그 동·호 행이 하나도 빠짐없이** 이 포장에 있다 | ✅ |
| `blocks` | 특정 품명 블록 **전체**다 | ✅ |
| `rows` | 위 둘로 설명되지 않는다 | ❌ 이 차수 전용 |

일부만 담긴 경우를 `units` 로 저장하면 다음 차수에 나머지까지 딸려 온다. 그래서 전량 포함을 확인한다.
기준을 못 뽑아내면 억지로 일반화하지 않고 `reusable = false` 로 남긴다 —
잘못 일반화한 규칙이 조용히 적용되면 포장이 통째로 뒤섞인 채 ERP에 올라간다.

검증: 우미 7차에서 저장한 동·호 규칙을 **8차에 적용**해 포장 9장이 그대로 재현되고
3,458장 전원이 배정됨을 확인했다 (`__tests__/packaging-rule.test.ts` + 실제 화면).

## 저장된 규칙은 권하기만 한다

같은 현장의 규칙이 있으면 포장 분리 자리에 버튼으로 띄우되 **자동 적용하지 않는다.**
차수마다 포장이 달라지는 현장이 있어, 조용히 바뀌면 사원이 알아채지 못한 채 ERP에 올리게 된다.

## 양식 프로파일은 거래처가 맞아야 적용한다

헤더 지문만으로 프로파일을 고르게 했더니 **KCC 프로파일이 우미 발주서에 적용돼 품목이 0건이 됐다.**
두 거래처가 동일유리 표준 양식을 같이 쓰기 때문에 지문(`위치|제품명|규격|수량|평수|실리콘|비고`)이
똑같은데 헤더 행은 12행과 13행으로 다르다.

그래서 **거래처나 현장이 맞을 때만 적용**하고, 지문은 같은 거래처의 프로파일이 여럿일 때 고르는 데만 쓴다
(`__tests__/form-profile.test.ts`). 여기에 더해, 프로파일을 적용했는데 품목이 0건이 되면
자동 판정으로 되돌리고 그 사실을 알린다 — 빈 결과를 조용히 내보내면 사원이
"이 발주서는 안 읽히나 보다" 하고 넘어간다.

# 큰 발주서 파일 다루기 — 화면이 멈추던 문제

KCC 여의도 발주서는 **144MB** 다. 시트는 1,057행뿐인데 이미지가 잔뜩 들어 있다.
이 파일을 올리면 화면이 통째로 멈추고 크롬이 "응답 없는 페이지" 를 띄웠다.

## 원인 두 가지

**① 같은 파일을 여러 번 파싱했다.** 시트를 고를 때마다 `XLSX.read` 를 3번 했다
(본 파싱 1회 + 열 지정 화면의 미리보기 글자 2회). 한 번이 10초를 넘으니 30초 넘게 멈췄다.
→ 파일을 고를 때 **딱 한 번** 읽어 `useRef` 에 들고, 원본 ArrayBuffer 는 버린다.
열 지정 화면에 쓸 글자도 그때 같이 뽑아 둔다.

**② `XLSX.read` 는 동기 함수다.** 브라우저에서 이 파일 하나가 13초쯤 걸리는데
그 동안 메인 스레드가 통째로 막혀 버튼이 하나도 안 눌린다.
→ 파싱을 **웹 워커**로 옮겼다 (`lib/parser/xlsx-worker.ts`, `lib/parser/read-workbook.ts`).

## 입력 형태로는 해결되지 않는다

| 방식 | 같은 파일 파싱 시간 |
|---|---|
| Node Buffer + `type:'buffer'` | **0.6초** |
| ArrayBuffer + `type:'array'` | 4.6초 |
| 바이너리 문자열 + `type:'binary'` | 4.8초 |
| Uint8Array + `type:'array'` | 5.7초 |

SheetJS 에 Node Buffer 전용 빠른 경로가 있어서 Node 가 10배 빠르다.
브라우저에서 쓸 수 있는 입력은 전부 5초 안팎이라 **형태를 바꿔서는 못 줄인다.**
그래서 줄이는 대신 메인 스레드 밖으로 뺐다.

## 결과 (144MB 파일 기준)

| | 고치기 전 | 고친 뒤 |
|---|---|---|
| 파일 로딩 중 **화면이 멈춘 가장 긴 시간** | 13,000ms | **187ms** |
| 시트 클릭 | 30초 초과 (버튼이 안 눌림) | 1.2초 |
| 포장 분리 방식 전환 | — | 0.8~1.2초 |

워커를 못 쓰는 환경이면 예전처럼 동기로 읽는다 — 느릴지언정 동작은 해야 한다.

# 정정: 합친 호들의 실명은 자동으로 정해진다

전에 이 문서와 `CLAUDE.md` 에 "여러 호를 합칠 때의 실명 선택은 자동 판정이 불가능하다" 고 적어 두었다.
**틀렸다.** 실물 ERP 9시트를 전수 대조해 보니 규칙이 일관돼 있었다.

## 무슨 상황인가

3동 1~3호 455×950 은 한 줄로 합쳐지는데, 발주서의 실명이 호마다 다르다.

| 호 | 수량 | 실명 |
|---|---|---|
| 1호 | 10장 | 주방/식당(外) |
| 2호 | **20장** | **주방/식당,드레스룸(外)** |
| 3호 | 10장 | 주방/식당(外) |

2호만 20장인 이유는 **드레스룸 창도 같은 455×950 규격**이기 때문이다. 오류가 아니다.

## 규칙: 포괄하는 쪽을 쓴다

합쳐진 줄은 세 호의 창을 **전부** 담으므로 라벨도 전부를 가리켜야 한다.
첫 값(`주방/식당`)을 쓰면 2호의 드레스룸 창이 라벨에서 사라진다.

실물 ERP 9시트가 예외 없이 포괄하는 쪽을 적었다:

| 포장 | 실물 표기 |
|---|---|
| 3동 1~3호 (40장) | 주방/식당,**드레스룸** |
| 3동 4,5호 (20장) | 주방/식당 |
| 2동 1,2호 | 드레스룸,**팬트리** |

이 규칙을 넣은 뒤 **우미 7차 136행이 위치 문자열까지 전부 실물과 일치**한다
(전에는 118행만 일치하고 18행을 "판단 불가" 로 남겼다).

## 문서마다 표기가 다르다

| 문서 | 표기 | 근거 |
|---|---|---|
| ERP 업로드 엑셀 | `주방/식당,드레스룸` | ERP-2026년.xlsx 9시트 전부 |
| 작업의뢰서 | `주방/식당` | 26-1952 스캔본 |

작업의뢰서는 회사 ERP 가 뽑아 주는 문서라 우리 출력물이 아니다 — 줄여 쓰는 건 ERP 의 표기 습관으로 보인다.
그래서 하나로 강제하지 않고 `RoomPolicy` 로 나눴다 (ERP 엑셀 `widest`, 작업의뢰서 `first`).

## 여전히 사람에게 묻는 경우

실명이 **포함 관계가 아닐 때**다 (예: `거실` 과 `침실`). 그때만 확인 요청을 띄운다.
우미 7차에는 그런 행이 하나도 없어 경고가 0건이 됐다.
